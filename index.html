braino

brainwaves → one instrument

A Muse headband reads delta through gamma off four electrodes. Those five numbers become oscillator frequencies, get snapped to a scale, summed to stereo and sent through a reverb tail. So far that's a synthesizer. What makes it braino is what else is allowed to reach the same knobs: a river gauge, the Schumann resonance, satellites passing overhead, solar wind, a fungus.

The 7.83 Hz standing wave in the cavity between the earth and the ionosphere sits inside the alpha band of a human brain. So when a live cavity reading bends the tuning table the notes are derived from, nothing is being compared to anything. The person and the planet are running through the same oscillator. Same band stream also renders to canvas, so a session comes out as sound and as an image of the same minutes.

the hard part: phase continuity. Frequency is interpolated up to audio rate and integrated rather than restarted per segment, so an hour of drifting EEG arrives as one unbroken tone instead of a chain of clicks. Then the patchbay: source, destination, depth and mode are all runtime decisions, and structural targets read your base slider value instead of the already-modulated one. Modulation bends around the setting rather than compounding against it, and pulling a cable heals it back.

Python · NumPy · Muse EEG · three.js · NOAA / KiwiSDR feeds

supermaker

weekly Angebote → price history

Follows the weekly offers at REWE, Lidl, ALDI and the rest, plus the organic Biomärkte. You tell it which products you actually buy and it charts what each one costs week to week. Mostly so I stop paying twice as much for the same yoghurt.

the hard part: two undocumented sources, an unofficial leaflet API and the page-data JSON sitting behind a Gatsby site, both had to come through one pluggable adapter. The daily fetch is slow and rate-limited, so it runs as a CI job instead. A stateful app with a database doesn't fit the serverless model underneath it.

Next.js · TypeScript · Drizzle · SQLite / Turso · GitHub Actions

artemator ↗

open calls → one dashboard

Scrapes art-funding open calls from a dozen sources, dedupes them, guesses region and type, flags what's new, tracks deadlines. A GitHub Action refreshes it every morning and redeploys. The whole point is that artists spend their evenings applying rather than searching.

the hard part: a dozen mismatched RSS and HTML feeds, deduped and self-checking, with nobody watching. When one of them quietly starts returning zero results it has to say so on the health strip. A silent source looks exactly like a slow week.

Python · SQLite · GitHub Actions · Netlify

synth detective ↗

track → patch notes

Name a track (Windowlicker, Da Funk, whatever) and it works out which synths probably made those sounds, then tells you how to patch them yourself. Music-nerd archaeology with an LLM behind a serverless API.

the hard part: getting structured, trustworthy patch data out of an LLM through a stateless function. And when the model hands back something unusable, which it does, the app has to fail into something readable rather than a stack trace.

spotitube

liked songs → local mp3s

Reads your Spotify Liked Songs, finds each one on YouTube, pulls it down as an MP3. A small command-line pipeline for keeping an offline copy of a library that otherwise only ever lives in someone else's cloud.

the hard part: matching a Spotify library to YouTube when the two share no identifiers. Fuzzy hits, wrong-length uploads, live versions, all of it has to be filtered down to the one correct audio match. It stays testable too, with a fully mocked suite that needs no network and no credentials.

Python · Spotify API · yt-dlp · pytest

kalendarski ↗

weather → color

A macOS-style calendar whose background is an hour-by-hour temperature heatmap. Your week, painted by the forecast. Night hours go blue, afternoons run red, and the whole grid repaints as the weather changes.

the hard part: repainting the calendar from live hourly forecasts without hammering the API. Weather gets cached and interpolated between fetches, which keeps the gradient smooth instead of stepping every time a request lands.

React · TypeScript · Vite · OpenWeatherMap

About

the person behind the waveform

I'm Oleksandr. Sasha to most people. Engineer from Lviv, living between Hamburg and Gießen. Ten years of production Java and Python behind me. These days I design and ship AI agents at taliox, where the job is making LLM systems that hold up once real users get to them.

Before the web work I was a research engineer on JRODOS, the EU's nuclear-emergency decision-support system, as a doctoral researcher (аспірант) at the Institute of Mathematical Machines and Systems (NASU, Kyiv) under Mark Zheleznyak. My part was the engineering layer around the hydrological models: Java plugins, model wrappers, GIS pipelines for radionuclide transport in rivers. Chernobyl contamination maps. The Niida catchment for the Fukushima group. A real-time exchange pushing WRF forecasts between Ukraine and Romania so the Prut could be watched for transboundary flooding. I never finished the dissertation. The engineering stayed.

That's the thread, more or less. Most of what's here starts with a signal (weather, a river, a brain, a shopping list) and ends up as a system that does something with it. The waveform at the top of the page works the same way: hit ▶ hear this waveform and it plays itself back as audio. Sound has always been half of why I build any of this.
